# 安全の仕組み

## 人と機械の見分け方

人・司令塔・ワーカーは、同じ GitHub のアカウントで書く。GitHub App や機械用のアカウントは使わない。そのため、書き手のアカウントでは人と機械を見分けられないので、目印の考え方を次のようにする。

- 機械を動かす人の書き込み（人の意図）は、クライアントが署名して、private の状態リポジトリの `intents/` にだけ書く。司令塔とワーカーは、署名を確かめられた人の意図だけを指示として扱う
- 各リポジトリの Discussion・PR（public なら誰でも書ける）は、機械が指示として読まない。人の意図の写しは、司令塔が人の読める形で書く
- 目印の無い書き込みは、同じアカウントのものでも指示として扱わない。人が自分の Claude のセッションから PR にコメントしても、ループは動かない
- 機械が書くものの目印は、1 つの書式にそろえて版の番号を付ける。読み書きは 1 つのライブラリだけで行う

人の意図にあたるもの: 依頼・回答・説明を求める・ゴールの修正・開始・取り下げ・最終 PR への指示・判断のカードへの答え・マージの承認・引き継ぎ・人がする作業の完了（Secrets の登録を含む）・実機確認の「確認した」「問題あり」・リリースの操作（審査に出す・配信する など）・リポジトリの登録と外す・テンプレートからの作成・保護の設定。

## 人の意図の署名

### 鍵

- クライアントの端末ごとに鍵を作る。方式は ECDSA P-256（iPhone・Mac の Secure Enclave と Android の Keystore の両方で、鍵を端末の外に出さずに扱える）
- 鍵は、端末のロックが解除されている間なら、Face ID・Touch ID なしで使える（Siri やショートカットなど、クライアントの画面の外からも署名できるようにするため）。鍵はその端末の外に出さない（Secure Enclave の鍵で、Keychain の項目もその端末だけ・ロック解除中だけ読める設定にする）
- 端末を失くした・盗まれたときは、ほかの端末か非常口の鍵で、その端末の鍵を取り消す

### 署名する中身

古い指示の貼り直しや、承認の後の差し替えを通さないために、次をすべて署名に含める。

| 項目 | 例 |
| --- | --- |
| 版 | 署名の形式の版 |
| 意図の種類 | 回答・開始・マージの承認 など |
| リポジトリ | owner/repo |
| 対象の id | 質問の id・Discussion・PR の番号 |
| 対象の版 | PR の head のコミット・ゴールの版 |
| 本文のハッシュ | 回答や指示の本文 |
| 時刻 | 署名した時刻 |
| 一度しか使えない番号 | 使った番号は状態リポジトリに記録し、二度目は断る |
| 鍵の id | どの端末の鍵か |

- 署名する文字列のそろえ方（項目の並び・改行・文字の正規化）を決め、Swift と Kotlin で同じ結果になることをテスト用の例で確かめる（RFC 8785 などを候補にする）
- マージの承認は対象の版（head のコミット）に結びつくので、承認の後に push された変更は、承認し直すまでマージしない

### 公開鍵の一覧

- 登録済みの公開鍵の一覧は、「登録済みの鍵が署名した追記の記録の列」として持つ。どこに置いても、改ざんされていないかを確かめられる
- 司令塔とワーカーは、セットアップのときに最初の鍵の指紋を手で固定する。一覧と指紋は Keychain に置く（下の「秘密の置き場所」）
- 新しい端末の鍵は、登録済みの端末で承認して登録する
- 端末をなくしたときは、ほかの端末から取り消しの記録を書く
- 非常口: クライアントが壊れても人の意図を出せるように、Mac のコマンドから署名できる鍵を 1 本登録しておく。普段使いのクライアントは、作りかけの版ではなく安定した版を入れる

### 共同開発者（後から足す）

最初の版では対応しないが、後から足せる作りにしておく。

- 鍵を GitHub のアカウントに結びつける。司令塔とワーカーは、署名・書き手のアカウント・そのリポジトリへの書き込み権限を確かめる
- リポジトリごとに、役割（依頼・回答・開始・マージ・リリース）を持てる形にする
- 状態はリポジトリごとに分けて置き、後で見せる範囲を分けられるようにする
- Claude を使うジョブは、依頼した人の Mac と、その人の Claude の契約で動かす。他人の依頼を自分の契約で処理しない

## 秘密の置き場所

- 秘密（GitHub のトークン（持ち主ごとの毎日のものと、管理用のもの）・Claude の setup-token・APNs の鍵・App Store Connect の API キー・公開鍵の一覧と最初の鍵の指紋）は、Keychain だけに置く。ファイルや環境変数には置かない
  - APNs の鍵は、Apple Developer から落とした .p8 のファイルを `askhub-commander apns` が読んで Keychain に置く（.p8 は 1 行に収まらず、端末で伏せて入れられないため）。置いた後は、.p8 を Mac に残さない（[operations.md](operations.md) の「通知」）
- Keychain の項目は、読めるアプリを署名したワーカーと司令塔に限る。ほかのプロセスが読もうとすると確認の画面が出るが、画面の無い実行では許可できないので失敗する。見覚えの無い確認の画面が出たら拒否する
- ワーカーと司令塔は Developer ID で署名し、Hardened Runtime を付ける。署名は常時オンの Mac で行い、署名の鍵は CI（GitHub の Secrets）に置かない（[operations.md](operations.md) の「署名と公証」）。同じ識別子とチームで署名し続ければ、更新しても Keychain の許可が続く
- Keychain はログインしている間だけ開く。常時オンの Mac は、再起動の後にログインが要る
- 司令塔とワーカーは、ログイン中のセッションの LaunchAgent として動かす。ssh のセッションからは Keychain を読めず（User interaction is not allowed）、LaunchAgent からは読めることを段階 0 で確認した

## Claude の隔離

Claude とビルド・テストは、ワーカーと同じ macOS のユーザーで動かす。別のユーザーは作らず、次の対策を重ねる。

- **権限**: `dontAsk`（許可の一覧にある操作だけ通し、ほかは自動で断る）にする。`bypassPermissions` は使わない
- **書ける範囲**: Claude のファイルの読み書きの道具と Bash を、その epic の作業場所だけに絞る。Bash は sandbox の中で動かす。sandbox が囲うのは Bash とその子プロセスだけなので、ファイルの道具は許可の規則で絞る
- **通信**: sandbox の通信の許可は最小にし、github.com は入れない（持ち出しの経路になるため）。依存の取得は、Claude を呼ぶ前にワーカーが済ませる。WebFetch と WebSearch は許可しない
- **資格情報を渡さない**: Claude を起動するときも、ワーカーがビルドやテストを流すときも、環境変数を作り直してトークンを含めない
- **リポジトリ側の設定を効かせない**: `claude -p` はフォルダの信頼の確認を出さないので、通常の起動では、リポジトリの `.claude/settings.json` の hooks（SessionStart・PreToolUse）と環境変数、`.mcp.json` のサーバーがそのまま動く（段階 0 で確認）。ワーカーは `--restricted --strict-mcp-config` と専用の設定フォルダ（`CLAUDE_CONFIG_DIR`）で Claude を起動する。この形では、どれも効かず、人の `~/.claude` の指示も見えないことを確かめた。設定は `--settings` で渡すものだけにする（setup-token は `--bare` と一緒に使えないので、`--bare` は使わない）
- **Claude に git を許可しない**: sandbox の中でも `git commit` はでき、worktree では共有の `.git` にも書ける（段階 0 で確認）。commit と push はワーカーが行う
- **ワーカーの git を守る**: 作業場所の `.git/config`（`core.hooksPath`・`core.fsmonitor`）や `.git/hooks` が書き換えられていても、ワーカーの権限でコマンドが動かないよう、hooks と fsmonitor を無効にする設定を付けて git を動かす。`.git/config` を前後で比べる
- **Xcode のスクリプト**: スクリプトが触れるファイルを宣言したものだけに限る設定（User Script Sandboxing）を、テンプレートで必ず有効にする
- **危ない変更は人に回す**: 依存の追加・ビルドのスクリプト・ワークフロー・`Package.swift` のプラグイン・`.claude/`・`.mcp.json` の変更があったら、ビルドやマージの前に人の確認を挟む
- **残るリスク**: 乗っ取られた依存や誘導されたコードがテストで動いた場合、Keychain の外にあるファイル（ほかのリポジトリの clone など）は読まれる可能性が残る。手で開発しているときに依存が乗っ取られた場合と同じ水準として受け入れる

## トークン

- 役割ごとにトークンを分け、権限を絞る

  | 役割 | 権限 |
  | --- | --- |
  | ワーカー | 対象のリポジトリの Contents・Pull requests・Issues・Discussions と、状態リポジトリ。Workflows・Secrets・Administration は持たない |
  | 司令塔 | ワーカーと同じ範囲と、通知に要る読み取り |
  | 司令塔の管理用 | Administration・Secrets・Environments・Workflows の書き込み（と Contents・Pull requests）。署名した人の意図を処理するときだけ使う（下の「管理用のトークン」） |
  | クライアント | 状態リポジトリだけ。人の操作（マージ・Secrets の登録・保護の設定など）は、署名した意図として状態リポジトリに書き、司令塔が行う |
  | GitHub Actions | 状態リポジトリには書かない。司令塔の見張り（`Commander/Watch`）が `GITHUB_TOKEN` で状態リポジトリに Issue を立てるだけ。App Store Connect の状態は司令塔が読む（[release.md](release.md) の「ワークフロー」） |

- 対象のリポジトリは複数の organization にまたがる。fine-grained token は 1 つの持ち主のリポジトリしか扱えないので、持ち主（organization・個人）ごとに 1 つ作り、Keychain に持ち主の名前で置く。ワーカーと司令塔は、リポジトリの持ち主でトークンを選ぶ。権限は、Contents・Pull requests・Issues・Discussions・Actions（揺らいだ CI の流し直し）の読み書きと、Commit statuses の読み取り（Checks は fine-grained token では選べない。check runs は public のリポジトリなら権限なしで読める）。Workflows は付けない（ユーザーの決定。classic token は権限を絞れないので使わない）
- トークンの期限を状態リポジトリ（生きている印の自己診断）に記録し、14 日前からクライアントで知らせる。値は記録しない（[operations.md](operations.md) の「トークンの期限」）

### 管理用のトークン

保護の設定（ルールセット）・テンプレートからの作成・Discussions を有効にする・Secrets の登録・ワークフローのファイルを変える PR は、毎日のトークンではできない。
そこで、常時オンの Mac の Keychain に、持ち主ごとの管理用のトークンを別に置く（2026-11-12 に決めた。入れ方は [operations.md](operations.md) の「管理用のトークン（持ち主ごと）」の `askhub-commander admin-token <持ち主>`）。

- 毎日のトークン（Claude の書いたコードを push するもの）には、Administration・Secrets・Workflows を足さない。リポジトリの削除・保護の解除・ワークフローの書き換えができるトークンを、毎日の push に使わない
- 使うのは司令塔だけで、署名した人の意図を処理するときだけ使う（保護の設定・作成・Secrets の登録・対象に加えるときの準備）。自動では使わない
- git の credential helper と、ワーカー・Claude のジョブには渡さない
- 毎日のトークンとは、Keychain の名前（`github-admin-token/<持ち主>`）も読む部品（`GitHubAdminTokens`）も分ける。git の credential helper は毎日のトークンの部品しか受け取らないので、管理用のトークンが git に渡る道は無い。毎日のトークンと同じ値は入れられない
- 権限は Administration・Secrets・Environments・Workflows の Read and write と、PR を出すための Contents・Pull requests の Read and write（Discussions のカテゴリを確かめるための Discussions の Read-only も付ける）。テンプレートから作るには、作る前のリポジトリを選べないので、その持ち主の All repositories が要る見込み（段階 4 の 5 で確かめる）
- 期限は毎日のトークンと同じく自己診断（`githubAdminTokens`）に書き、クライアントで知らせる。切れても毎日の仕事は止まらないので、「止まっています」にはしない。管理用のトークンが無い持ち主への操作は、理由を書いて断る
- ワークフローのファイルを変える PR は、ワーカーの epic では push できない（ワーカーは Workflows を持たない）。司令塔が決まった手順で PR を出し、人が承認してからマージする（[operations.md](operations.md) の「対象のリポジトリ」）
- Secrets の値は、クライアントが GitHub の公開鍵で暗号化し、司令塔は暗号文を渡すだけ（[flows.md](flows.md) の「人がする作業」）

## public のリポジトリと Secrets

アプリのリポジトリの多くは public で、ブランチへの push で動くワークフローには Secrets が渡る。ワーカーが push する変更から Secrets に届かないよう、次の決まりにする。

- ワーカーのトークンに Workflows の書き込み権限を持たせない。ワークフローのファイルを含む push は GitHub が断る
- Secrets は Environment の Secrets にし、使えるブランチを develop・`release/**`・main に限る
- 自動マージの手動の条件に、ワークフロー・道具・ビルドのスクリプトの変更を入れる（[flows.md](flows.md) の「マージの規則」）
- 共通リポジトリのワークフローは、動くタグではなく固定したコミットで呼び、版はクライアントから上げる（または、タグを保護する）
- Claude に渡すレビューの指摘は、決まった書き手（CodeRabbit など）のものだけにする。public のリポジトリには誰でもコメントを書けるため

## ブランチ保護

- 保護の目的は、機械のミスを防ぐこととする
- develop・main・`release/**` は、ルールセットで PR 必須・必須チェック・force push と削除の禁止にそろえる。ルールセットは管理者にも効くので、同じアカウントのトークンを持つワーカーや司令塔の直接の push も止まる（段階 0 で確認）
- 例外は作らない。リリースの後作業（バージョンを上げるコミット・main と develop への取り込み）も、司令塔が自分のトークンで PR を作り、CI が通ったら自動でマージする。アカウントのトークンで作った PR では CI が起動し、保護の下でマージできることを確かめた
  - `GITHUB_TOKEN` は、ルールセットの例外に入れられない（GitHub Actions のアプリが organization に属していないため）。既定の設定では PR も作れない。GitHub Actions に PR を作らせる設定は、オンにしない
- 今の組織のプランでは、private のリポジトリにルールセットを掛けられない。状態リポジトリ（private）の守りは、書き手ごとのファイル・版の確認・人の意図の署名で行う
- 保護の設定は、司令塔が自動で行わない。人がクライアントで押したときだけ、管理用のトークンで行う。ずれ（ルールセットが外れた・変わった）は定期的に点検して知らせる（段階 4 の 4 で作る。今は移すときに Claude のセッションが `gh` で手で掛けている）
