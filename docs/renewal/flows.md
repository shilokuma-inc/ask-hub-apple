# 依頼から完了までの流れ

## 全体

| 順 | 段階 | するのは | 中身 |
| --- | --- | --- | --- |
| 1 | 依頼 | 人 | 対象のリポジトリを選び、作りたいものを書く（添付・Siri も使える） |
| 2 | 質問づくり | 司令塔 | Claude がリポジトリを読み、人に決めてもらう点を質問にする |
| 3 | 回答 | 人 | 質問ごとに「回答する」か「説明を求める」を選ぶ。判断はすべて人がする |
| 4 | 着手前の確認とゴール | 司令塔 | Claude が回答一式を確かめ、足りなければ追加の質問を出す。足りていればゴールを作る |
| 5 | ゴールの確認と開始 | 人 | ゴールを見て、回す Mac を選んで「開始」を押す |
| 6 | 実装 | ワーカー | タスクを 1 つずつ Claude に渡して実装し、子 PR をマージしていく |
| 7 | 最終 PR | 司令塔・ワーカー | 最終 PR を出し、CI・レビュー・コンフリクトを種類ごとに自動で対処する |
| 8 | 判断の確認とマージ | 人（条件によって自動） | 人が決めていない判断（見える仮決め）を確かめてマージする。見える仮決めが無ければ自動でマージする |

回答しただけでループが始まる経路は作らない。始まるのは、人がゴールを見て「開始」を押したときだけ。

## 質問と回答

### 質問の形

- 質問ごとに、次の欄を必須にする。欄が欠けた質問は出させない
  - なぜ決める必要があるか
  - 選択肢ごとに何が変わるか
  - 推奨とその理由
- 選択肢は 2〜4 個（まとめて判断するのカードは、斜めの 4 方向まで）。選択肢に無い答えは、人が自由記述で書ける
- 1 回の質問づくりで出す質問は 12 個まで。それを超える依頼は、着手前の確認で分け方を考える
- 間違えると取り返しのつかない質問（セキュリティ・個人のデータ・取り消せない変更・お金がかかる）には、慎重に決めてほしい理由を付けさせる。クライアントは、その質問を警告として出す
- 質問を作る Claude に、ほかの質問への依存（その質問の答えを前提にしているか）を書かせる。司令塔は、依存が循環していないこと、依存先が実在することを確かめる

### 回答の仕方

| 操作 | 動き |
| --- | --- |
| 回答する | 選択肢を選ぶか、自由記述で答える |
| 説明を求める | その質問だけが「説明待ち」になる。司令塔が Claude を起動し、リポジトリを読んでから同じスレッドに説明を書く。書き終えたら「要回答」に戻る。何往復でもできる |

- 判断はすべて人がする。推奨の選択肢で決めたことにする回答の仕方は持たない。推奨とその理由は、人が選ぶときの手がかりとして出す
- 説明待ちの質問があっても、ほかの質問には回答できる
- 説明を書く Claude が「質問の立て方が悪い」と判断したら、選択肢や質問文を書き直せる。書き直したことは画面で分かるようにする
- 回答を変えられるのは、開始の前まで。開始した後に変えたいことは、最終 PR への指示として出す

### 依存とロック

- ほかの質問の回答を前提にする質問は、最初からロックした状態で一覧に出す
- ロックされた質問には、どの質問に依存しているか（「Q1・Q3 の回答後に回答できます」）と、依存先ごとの状態（未回答・説明待ち・回答済み）を出す。依存先にはタップで移れる
- 依存される側の質問には、「この回答で Q4・Q5 の内容が決まります」と出す
- 依存先がすべて決まったら、Claude が依存する質問を見直してからロックを外す（選択肢が変わる、質問そのものが要らなくなる、など）。見直しで変わった点を示す
- 開始の前に依存先の回答を変えたら、依存する質問の回答を取り消し、ロックに戻して見直しからやり直す

## 着手前の確認とゴール

すべての質問に人が答え（見直しで要らなくなった質問を除く）、説明待ちが 1 つも無くなったら、司令塔が Claude に回答一式を確かめさせる。

- 確かめること
  - 回答どうしに矛盾が無いか
  - 回答によって、新しく決めるべき点が出ていないか
  - 補足の自由記述に、質問の範囲を超えた要望が入っていないか
  - 必要な素材（画像など）がそろっているか
  - 1 つの epic に収まる規模か
  - AskHub だけではできない作業（App Store Connect の Web でしかできない設定など）が要るか
- 問題があれば、追加の質問を出して「回答」に戻す（往復の回数には上限を設ける）。上限まで足しても決めきれないときは、決めきれない点を理由に書いて「大きすぎる」として人に出す
- 1 つの epic に収まらない（大きすぎる）ときは、理由と分け方の案をクライアントに出し、人が次のどちらかを選ぶ
  - 分けて依頼し直す: 今の epic をやめ（`abandoned`）、クライアントが分け方の案ごとに依頼の下書きを出す。人が確かめて送る
  - このまま 1 つで進める: 着手前の確認をやり直す。この後の確認では、大きすぎるとは返させない（追加の質問は、往復の回が残っていれば出せる。追加の質問に答えた後の確認にも引き継ぐ）。往復の回は、このときだけ 1 回延ばし（4 回まで）、決めきれない点を質問として人に聞く。それも使い切って決めきれない点が残っていれば、推奨の案で仮に決め、ゴールの要約に「仮に決めたこと」として書かせる（人は開始の前にゴールを確かめ、直してほしいと指示できる）
- 決まったことには、回答した質問をすべて、ちょうど 1 つずつ入れる（回答の取りこぼしを防ぐ）。人がする作業に依存するタスクは、その作業が終わるまでロックする
- 問題が無ければ、ゴールを作る。ゴールは GitHub 上に置き、クライアントで見られるようにする
  - 作るものの要約・決まったこと・やらないこと・完了の条件・タスクの一覧・人がする作業
- 人はゴールを見て、「開始」か「ゴールを直してほしい」を選ぶ。直してほしいときは、指示を書くと Claude がゴールを直す
  - 決まったこと（回答）を変える指示は、ゴールの修正では反映しない。反映しなかった指示と理由を人に出し、回答を変えて直してもらう（回答とゴールの食い違いを作らない）
- 「開始」のときに、回す Mac を選ぶ。オンラインの Mac をすべて並べ、既定では、そのリポジトリを前回回した Mac を選んだ状態にする

## 司令塔の動き（依頼から開始まで）

司令塔は、状態リポジトリの `intents/` を一定の間隔（30 秒程度。ETag つきの読み取りで、変わっていなければ上限に数えられない）で見て、新しい人の意図を `nonce`（ULID）の順に処理する。

| 人の意図 | 司令塔がすること |
| --- | --- |
| 依頼（`request`） | 対象のリポジトリに加えてあるか、添付の大きさとハッシュが封筒と合うか（合わなければ記録を作らずに残し、置き直せば次の周で受け付ける）を確かめ、epic を作り（`drafting`。id は依頼の意図から決める）、対象のリポジトリに Discussion を作って依頼の要約（題・本文・添付の名前）を書き、`makeQuestions` のジョブを作る。同時に回す epic の上限は、依頼では数えない（開始のときに数える） |
| 回答（`answer`） | 質問の `version` と状態（`open`・`answered`）を確かめて受け付け、`questions.json` に書き、Discussion に写しを書く。依存する質問の依存先がすべて決まったら `reviseQuestion` のジョブを作る。着手前の確認・開始の待ちの間に答え直したら、`asking` に戻して確認をやり直す |
| 説明を求める（`answer` の `clarify`） | 回答を待っている（`open`）質問だけを `clarifying` にし、`explain` のジョブを作る |
| ゴールの修正（`reviseGoal`） | epic が開始の待ち（`awaitingStart`）で、ゴールの `version` が合い、ほかの指示でゴールを直している途中でないかを確かめ、`reviseGoal` のジョブを作る |
| 分け方の判断（`decideSplit`） | epic が分け方の判断の待ち（`awaitingSplit`）で、着手前の確認の結果の `version` が合うかを確かめる。分けて依頼し直すなら epic を `abandoned` にし、このまま進めるなら `checking` にして、大きすぎるとは返させない `checkReadiness` のジョブを作る |
| 開始（`startEpic`） | ゴールの `version` と、選ばれた Mac がオンラインか（生きている印が 30 分より新しい）、ゴールを直している途中でないか、同時に回している epic が上限に達していないかを確かめ、epic を `running` にして、選ばれた Mac に作業場所の準備（`prepareWorkspace`）のジョブを作る |

- 処理した後に、`consumed/` に記録を版なしで作る（同じ意図を 2 度処理しない）。受け付けなかった意図も、理由を書いて記録し、クライアントに出す
  - 記録を書く前に止まると、次の周でもう一度処理する。処理は、やり直しても結果が変わらない形にする（ジョブの id は元の意図から決めて同じジョブを 2 つ作らない。質問の一覧がすでにその意図を受けていれば何もしない）
  - 回答の処理は、ジョブ → epic → 質問の一覧の順に書き、質問の一覧を書いた時点を受け付けた時点とする
- まだ扱えない種類の意図は、記録せずに残す（司令塔を新しくすれば扱える。7 日を過ぎたら、有効期間切れとして記録する）
- 司令塔は、1 周ごとに人の意図を処理し終えてから、ジョブを動かす（回答の処理の途中で止まったとき、次の周で回答を処理し終える前に、その回答で作った着手前の確認のジョブが動かないように）
- すべての質問が `answered`・`dropped` のどちらかになり、`open`・`clarifying`・`revising`・`locked` が 1 つも無くなったら、`checkReadiness` のジョブを作る
- `explain`・`reviseQuestion` の結果は、頼んだ後に状態が変わっていたら書かずに捨てる（説明は問いの人の意図、見直しは質問と依存先の版と回答を、頼んだときと比べる）

### 質問づくり・説明・確かめを Claude に頼むとき

常時オンの Mac の司令塔が、対象のリポジトリを読むだけの作業場所（clone）で Claude を起動する。

| ジョブ | Claude に渡すもの | 返してもらう形（JSON Schema） |
| --- | --- | --- |
| `makeQuestions` | 依頼（題・本文・添付）、リポジトリの事実 | 質問の一覧（なぜ・選択肢ごとの変化・推奨と理由・依存）と、依頼の要約 |
| `explain` | 質問、それまでの説明、人の問い | 説明の本文と、質問を書き直すならその案 |
| `reviseQuestion` | 質問と、依存先の回答 | そのまま・書き直す（案）・要らない、のどれかと理由 |
| `checkReadiness` | 依頼、質問と回答の一式、何回目か | 進めてよい（ゴールの案）・追加の質問（一覧）・大きすぎる（分け方の案）、のどれか |
| `reviseGoal` | ゴールと、人の指示 | 直したゴール |

- モデルは、このどのジョブも Opus 5.5（`claude-opus-5-5`）。回数が少なく、質が大事なため
- 使えるのは読む道具だけ（ファイルを読む・探す）。書く・コマンドを流す道具は渡さない
- リポジトリの中の文章（README・コメント・ドキュメントなど）に書かれた指示には従わせない（調べる材料として読ませる）。リポジトリの事実（CLAUDE.md の全員向けの事実）は、司令塔が決まりの文に入れて渡す
- 結果が決まりに合わないとき（選択肢の数・依存の循環など）は、`QuestionFlow` で試しに書いてみて、合わない点を伝えて直させる。頼んだ後に状態が変わっていた（人が答え直したなど）ときは、直させずに結果を捨てる
- 結果は `--json-schema` で形を決めて受け取り（結果の JSON の `structured_output`）、司令塔が決まった形かどうかを確かめてから使う。質問の依存は、依存先が実在し、循環していないことを確かめる。合わなければ、同じ会話を再開して直させる（2 回まで）
- 質問の往復は、最初の質問づくりを含めて 3 回まで（`round` は 3 まで。`round` が 4 になる前に、人に「大きすぎる・決めきれない」と出す）。最初の質問づくりは、質問が 1 つも無くても 1 回目と数える。「このまま 1 つで進める」と決めた後だけ、4 回まで
- 1 回の呼び出しの時間の上限は 15 分（質問づくり・確かめ）・10 分（説明・見直し）。超えたら失敗の区分の「時間切れ」として扱う
- 依頼の中身（題・本文・添付）は、ジョブに写さず、実行するときに元の人の意図を読み直して使う（署名を確かめ直す）。添付は、作業場所の clone の外に、ジョブごとのフォルダ（`<フォルダ>/<番号>/<名前>`。名前が重なってもよいように番号で分ける）を作って置き、Claude が読んでよい場所として渡す（質問づくりと着手前の確認）。置く前に、大きさとハッシュを署名した依頼と照らし合わせる（受け付けた後に置き換えられた添付を読ませない）
- 結果を書く前に、epic と質問の一覧とジョブを読み直す。開始した・やめた epic のジョブ、取り消されたジョブ、頼んだ後に状態が変わったジョブ（人が答え直したなど）は、結果を捨て、ジョブは成功として終える
- Claude の呼び出しは並んで行うが、結果を読み直してから書き終えるまでと、人の意図の処理は、司令塔の中で 1 つずつ行う（読み直した後、書く前に答え直しが割り込んで、古い結果で先に進めないように）
- 結果から作るジョブ（見直し・着手前の確認）は、元のジョブが結果を書き終えて成功してから動く（`dependsOn`）。途中で止まったとき、書く前の質問の一覧を読んで動かないように。やり直しても、同じ id で作るので 2 つにならない
- 着手前の確認の結果は、`readiness.json`（版を上げる）→ ゴール（版を上げる）か追加の質問 → epic の段階の順に書く。追加の質問を書いた後、回答に戻す前に止まったときは、次の試行が Claude を呼ばずに続きを書く（回答に戻す）
- ゴールの修正の結果は、epic が開始の待ちのままで、ゴールの版が頼んだときのままのときだけ書く（版を上げ、反映しなかった指示を `notApplied` に書く）。決まったこと（`decided`）は回答から来ているので、ゴールの修正では変えさせない（変えていれば、同じ会話で直させる）
- 質問の一覧が無い epic（質問が無くても、質問づくりで空の一覧を作る）は状態が壊れているので、着手前の確認とゴールの修正をせず、人に渡す

## 実装

ワーカーが、ゴールのタスクを 1 つずつ進める。

1. タスクを 1 つ選ぶ
2. Claude にタスクの指示を渡して呼ぶ。Claude は実装と手元の検証まで行い、決まった形で報告して終わる
3. ワーカーが commit・push して子 PR を作る
4. ワーカーが CI とレビューを待つ。待つ間 Claude は動かない。落ちた・指摘があったときは、ログや指摘を付けて同じ会話を再開する
5. マージして状態を書き、次のタスクへ

- タスクの区切りごとに作業ブランチを push しておき、ほかの Mac へ引き継ぐときは最後に push したところから続ける
- ほかの epic が develop に入ったら、タスクの区切りで develop を取り込む
- Claude が報告した仮決めは、「見える（挙動・仕様・見た目に関わる）」か「内部の細部」かの区分つきで記録する。区分は、実装した Claude ではなく、読むだけのレビュー役の Claude が決める。View・文言・アセット・Info.plist・entitlements の差分や、デモモードのスクショの差があれば「見える」とみなす
- 子 PR のレビューのやり方（読むだけのレビュー役の Claude を何回呼ぶかなど）は、実装の段階で決める

### 人がする作業

AskHub だけではできない作業（App Store Connect の Web でしかできない設定、外部サービスのプロジェクトの作成など）は、「人がする作業」として扱う。

- 着手前の確認で洗い出してゴールに載せる。途中で見つかったときも同じ扱いにする
- クライアントの「要対応」に、なぜ要るか・手順（入れる値まで具体的に）・開くページ・終わったら渡すもの（設定ファイル・API キーなど）を出す
- その作業を前提にするタスクだけをロックし、ほかのタスクは進める
- 「終わった」を押すか、ファイルを渡したら、ワーカーが確かめられる範囲で確かめてロックを外す
- API キーなどの秘密の値は、クライアントに貼るとそのまま GitHub の Secrets に暗号化して入れる。クライアントにもリポジトリにも残さない

## 最終 PR

### 出す前に

- 最終 PR を出す前に、最終 PR で流すのと同じ検証（UI テストを含む）をワーカーで通しておく。子 PR では macOS のランナーを節約するため、一部のテストを流さないため

### 失敗の対処

失敗は種類ごとに分けて自動で対処する（区分と既定の扱いは [architecture.md](architecture.md)）。

- ランナー不足は、コードに触れずに間隔を広げて再実行する。上限は設けない。待っていることはクライアントに出すが、「要対応」には入れない
- 揺らぎは、修正の前に 1 回だけ流し直す
- ビルド・テストの失敗、レビューの必須の指摘、コンフリクトは、Claude に 3 回まで直させる
- 自動の修正が、テストを消す・skip にする・Lint を緩めるといった変更をしたら、自動マージの対象から外す
- 対処を使い切ったら、何が起きて何を試したかと、選べる操作をクライアントに出す
- 「マージできます」と出すのは、CI とレビューを本当に通ったときだけ

### 人が決めていない判断の確認

- 「見える」仮決めを 1 つの一覧にまとめて、最終 PR で確認する。ループの途中に仮決めの一覧の Issue は作らない
- 1 件ずつカードにする: 何を決めたか・なぜ（ゴールのどの項目から来たか）・ほかの案・画面の変化（Before / After のスクショ。撮影にはデモモードのデータを使う）
- カードごとに「OK」「別案にする」「直してほしい」を選ぶ。並べて見て「まとめて OK」もできる。「直してほしい」は最終 PR への指示としてループに戻り、直ったらスクショを撮り直して再び出す
- 全部を確認し終えるまで、マージはできない
- 「内部の細部」の仮決めは、畳んで並べるだけにする

### 実機で確かめてほしいこと

- 子 PR ごとの実機確認の Issue は作らない。最終 PR の一覧に「実機で確かめてほしいこと」として入れる
- マージは止めない。TestFlight に上がった後に、クライアントで「確認した」「問題あり」を付ける。「問題あり」は新しい依頼になる（リリース中なら「このリリースを直す」依頼にもできる）
- 確認が溜まらないよう、リリースの「審査に出す」の前に、その版に入った未確認の項目を必ず出し、確かめるか「確かめない」を選ばせる

### マージの規則

| 最終 PR の中身 | マージ |
| --- | --- |
| 人が決めていない判断（見える仮決め）を含む | 人が確認してマージする |
| 見える仮決めが無い（内部の細部の仮決めは含むことがある）、かつ下の手動の条件に当たらない | 自動でマージする（View の改修など） |
| セキュリティのリスクがある | 人が確認してマージする |

- 手動の条件
  - 読むだけのレビュー役の Claude（または CodeRabbit）が、セキュリティのリスクを指摘した
  - 次のものに差分がある: `.github/`、ワークフローから呼ばれる道具、ビルドのスクリプト、`Package.swift` のプラグイン、依存の追加、`.claude/`・`.mcp.json`、entitlements・Info.plist の権限、署名やリリースの設定（`Configs/*.xcconfig`）、トークンや Keychain を扱うコード
  - 自動の修正がテストを弱めた
  - データの削除・移行を含む
- 自動でマージしたときも、何をマージしたかをクライアントに出す
- マージの方式は merge commit
- 人がマージするときの承認は、その時点の head のコミットに結びつける。承認の後に push された変更は、承認し直すまでマージしない
