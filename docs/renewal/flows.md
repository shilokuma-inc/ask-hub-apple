# 依頼から完了までの流れ

## 全体

| 順 | 段階 | するのは | 中身 |
| --- | --- | --- | --- |
| 1 | 依頼 | 人 | 対象のリポジトリを選び、作りたいものを書く（添付・Siri も使える） |
| 2 | 質問づくり | 司令塔 | Claude がリポジトリを読み、人に決めてもらう点を質問にする |
| 3 | 回答 | 人 | 質問ごとに「回答する」か「説明を求める」を選ぶ。判断はすべて人がする |
| 4 | 着手前の確認とゴール | 司令塔 | Claude が回答一式を確かめ、足りなければ追加の質問を出す。足りていればゴールを作る |
| 5 | ゴールの確認と開始 | 人 | ゴールを見て、回す Mac を選んで「開始」を押す |
| 6 | 実装 | ワーカー | タスクを 1 つずつ Claude に渡して実装し、子 PR をマージしていく |
| 7 | 最終 PR | 司令塔・ワーカー | 最終 PR を出し、CI・レビュー・コンフリクトを種類ごとに自動で対処する |
| 8 | 判断の確認とマージ | 人（条件によって自動） | 人が決めていない判断（見える仮決め）を確かめてマージする。見える仮決めが無ければ自動でマージする |

回答しただけでループが始まる経路は作らない。始まるのは、人がゴールを見て「開始」を押したときだけ。

## 質問と回答

### 質問の形

- 質問ごとに、次の欄を必須にする。欄が欠けた質問は出させない
  - なぜ決める必要があるか
  - 選択肢ごとに何が変わるか
  - 推奨とその理由
- 選択肢は 2〜4 個（まとめて判断するのカードは、斜めの 4 方向まで）。選択肢に無い答えは、人が自由記述で書ける
- 1 回の質問づくりで出す質問は 12 個まで。それを超える依頼は、着手前の確認で分け方を考える
- 間違えると取り返しのつかない質問（セキュリティ・個人のデータ・取り消せない変更・お金がかかる）には、慎重に決めてほしい理由を付けさせる。クライアントは、その質問を警告として出す
- 質問を作る Claude に、ほかの質問への依存（その質問の答えを前提にしているか）を書かせる。司令塔は、依存が循環していないこと、依存先が実在することを確かめる

### 回答の仕方

| 操作 | 動き |
| --- | --- |
| 回答する | 選択肢を選ぶか、自由記述で答える |
| 説明を求める | その質問だけが「説明待ち」になる。司令塔が Claude を起動し、リポジトリを読んでから同じスレッドに説明を書く。書き終えたら「要回答」に戻る。何往復でもできる |

- 判断はすべて人がする。推奨の選択肢で決めたことにする回答の仕方は持たない。推奨とその理由は、人が選ぶときの手がかりとして出す
- 説明待ちの質問があっても、ほかの質問には回答できる
- 説明を書く Claude が「質問の立て方が悪い」と判断したら、選択肢や質問文を書き直せる。書き直したことは画面で分かるようにする
- 回答を変えられるのは、開始の前まで。開始した後に変えたいことは、最終 PR への指示として出す

### 依存とロック

- ほかの質問の回答を前提にする質問は、最初からロックした状態で一覧に出す
- ロックされた質問には、どの質問に依存しているか（「Q1・Q3 の回答後に回答できます」）と、依存先ごとの状態（未回答・説明待ち・回答済み）を出す。依存先にはタップで移れる
- 依存される側の質問には、「この回答で Q4・Q5 の内容が決まります」と出す
- 依存先がすべて決まったら、Claude が依存する質問を見直してからロックを外す（選択肢が変わる、質問そのものが要らなくなる、など）。見直しで変わった点を示す
- 開始の前に依存先の回答を変えたら、依存する質問の回答を取り消し、ロックに戻して見直しからやり直す

## 着手前の確認とゴール

すべての質問に人が答え（見直しで要らなくなった質問を除く）、説明待ちが 1 つも無くなったら、司令塔が Claude に回答一式を確かめさせる。

- 確かめること
  - 回答どうしに矛盾が無いか
  - 回答によって、新しく決めるべき点が出ていないか
  - 補足の自由記述に、質問の範囲を超えた要望が入っていないか
  - 必要な素材（画像など）がそろっているか
  - 1 つの epic に収まる規模か
  - AskHub だけではできない作業（App Store Connect の Web でしかできない設定など）が要るか
- 問題があれば、追加の質問を出して「回答」に戻す（往復の回数には上限を設ける）。上限まで足しても決めきれないときは、決めきれない点を理由に書いて「大きすぎる」として人に出す
- 1 つの epic に収まらない（大きすぎる）ときは、理由と分け方の案をクライアントに出し、人が次のどちらかを選ぶ
  - 分けて依頼し直す: 今の epic をやめ（`abandoned`）、クライアントが分け方の案ごとに依頼の下書きを出す。人が確かめて送る
  - このまま 1 つで進める: 着手前の確認をやり直す。この後の確認では、大きすぎるとは返させない（追加の質問は、往復の回が残っていれば出せる。追加の質問に答えた後の確認にも引き継ぐ）。往復の回は、このときだけ 1 回延ばし（4 回まで）、決めきれない点を質問として人に聞く。それも使い切って決めきれない点が残っていれば、推奨の案で仮に決め、ゴールの要約に「仮に決めたこと」として書かせる（人は開始の前にゴールを確かめ、直してほしいと指示できる）
- 決まったことには、回答した質問をすべて、ちょうど 1 つずつ入れる（回答の取りこぼしを防ぐ）。人がする作業に依存するタスクは、その作業が終わるまでロックする
- 問題が無ければ、ゴールを作る。ゴールは GitHub 上に置き、クライアントで見られるようにする
  - 作るものの要約・決まったこと・やらないこと・完了の条件・タスクの一覧・人がする作業
- 人はゴールを見て、「開始」か「ゴールを直してほしい」を選ぶ。直してほしいときは、指示を書くと Claude がゴールを直す
  - 決まったこと（回答）を変える指示は、ゴールの修正では反映しない。反映しなかった指示と理由を人に出し、回答を変えて直してもらう（回答とゴールの食い違いを作らない）
- 「開始」のときに、回す Mac を選ぶ。オンラインの Mac をすべて並べ、既定では、そのリポジトリを前回回した Mac を選んだ状態にする

## 司令塔の動き（依頼から開始まで）

司令塔は、状態リポジトリの `intents/` を一定の間隔（30 秒程度。ETag つきの読み取りで、変わっていなければ上限に数えられない）で見て、新しい人の意図を `nonce`（ULID）の順に処理する。

| 人の意図 | 司令塔がすること |
| --- | --- |
| 対象に加える（`addRepository`） | `repo.json` を作る（同時に回す epic は 1 本）。すでにあればそのまま。段階 2 では設定を書くだけで、GitHub 側の準備（保護・Discussions）は後で足す |
| ビルドの設定（`configureRepository`） | 対象に加えてあるかと、設定の形（`build` の中の知らない欄も含めて）を確かめ、`repo.json` の `build` をまるごと置き換える（同じ設定なら書かない）。入れ方は [operations.md](operations.md) の「ビルドの設定の入れ方」 |
| 依頼（`request`） | 対象のリポジトリに加えてあるか、添付の大きさとハッシュが封筒と合うか（合わなければ記録を作らずに残し、置き直せば次の周で受け付ける）を確かめ、epic を作り（`drafting`。id は依頼の意図から決める）、`makeQuestions` のジョブを作る。対象のリポジトリの Discussion（依頼の題・本文・添付の名前）は、同じ周の最後の写しで作る（下の「Discussion の写し」）。同時に回す epic の上限は、依頼では数えない（開始のときに数える） |
| 回答（`answer`） | 質問の `version` と状態（`open`・`answered`）を確かめて受け付け、`questions.json` に書く（回答の写しは、周の最後の写しで Discussion に書く）。依存する質問の依存先がすべて決まったら `reviseQuestion` のジョブを作る。着手前の確認・開始の待ちの間に答え直したら、`asking` に戻して確認をやり直す |
| 説明を求める（`answer` の `clarify`） | 回答を待っている（`open`）質問だけを `clarifying` にし、`explain` のジョブを作る |
| ゴールの修正（`reviseGoal`） | epic が開始の待ち（`awaitingStart`）で、ゴールの `version` が合い、ほかの指示でゴールを直している途中でないかを確かめ、`reviseGoal` のジョブを作る |
| 分け方の判断（`decideSplit`） | epic が分け方の判断の待ち（`awaitingSplit`）で、着手前の確認の結果の `version` が合うかを確かめる。分けて依頼し直すなら epic を `abandoned` にし、このまま進めるなら `checking` にして、大きすぎるとは返させない `checkReadiness` のジョブを作る |
| 取り下げ（`abandonEpic`） | 開始する前（`drafting`〜`awaitingStart`）の epic を `abandoned` にし、epic の終わっていないジョブを取り消す（動いている Claude のジョブは、結果を書く前に epic を読み直して捨てる）。すでにやめていれば、ジョブの取り消しだけをして受け付ける。開始した後の取り下げ（作業のブランチの片付けなど）は段階 3 で決める |
| やり直す（`retry`） | 人の対応待ち（`waitingHuman`）のジョブで、試行の番号（`targetVersion`）が人の見たときのままかを確かめ、ジョブを `assigned` に戻す（担当の Mac がそのまま次の試行を引き受ける）。失敗の数え方は変えないので、同じ失敗が続けばまた人に渡る |
| やめる（`giveUp`） | 質問づくり・質問の見直し・着手前の確認をやめると epic が先に進めないので、epic ごと `abandoned` にして、epic の終わっていないジョブを取り消す（epic の段階の 1 回の書き込みで決まる。ほかの理由で取り消されたジョブでは epic をやめない）。説明をやめると、ジョブを取り消し、説明を待つ問いを外して質問を `open` に戻す。ゴールの修正をやめると、ジョブだけを取り消す（前のゴールのまま開始を待つ）。そのほかの種類は段階 3 で決める |
| 開始（`startEpic`） | ビルドの設定（`repo.json` の `build`）があるか、ゴールの `version` と、選ばれた Mac がオンラインか（生きている印が 30 分より新しい）、ゴールを直している途中でないか、同時に回している epic が上限に達していないかを確かめ、epic を `running` にして、選ばれた Mac に作業場所の準備（`prepareWorkspace`）のジョブを作る |

- 処理した後に、`consumed/` に記録を版なしで作る（同じ意図を 2 度処理しない）。受け付けなかった意図も、理由を書いて記録し、クライアントに出す
  - 記録を書く前に止まると、次の周でもう一度処理する。処理は、やり直しても結果が変わらない形にする（ジョブの id は元の意図から決めて同じジョブを 2 つ作らない。質問の一覧がすでにその意図を受けていれば何もしない）
  - 回答の処理は、ジョブ → epic → 質問の一覧の順に書き、質問の一覧を書いた時点を受け付けた時点とする
- まだ扱えない種類の意図は、記録せずに残す（司令塔を新しくすれば扱える。7 日を過ぎたら、有効期間切れとして記録する）
- 司令塔は、1 周ごとに人の意図を処理し終えてから、ジョブを動かす（回答の処理の途中で止まったとき、次の周で回答を処理し終える前に、その回答で作った着手前の確認のジョブが動かないように）
  - 1 周は 30 秒ごと: 人の意図の処理 → 試行を読んでジョブの状態を決める → 実装している epic のタスクを進めるジョブを作る（下の「タスクの流れ」）→ 自分宛ての Claude のジョブを、Mac ごとの同時の上限の中で引き受けて並んで動かす（Claude の呼び出しは周をまたいで動く）→ 状態を Discussion の写しと照らし合わせる。動かしているのに司令塔がまだ試行を読んでいないジョブは、引き受け直さず、空きも使っているとみなす
  - 生きている印（`commander.json` と、ワーカーとしての `macs/<mac>.json`）は 10 分ごとに書く。そのときに、7 日使っていないリポジトリの clone を消す
  - この Mac が引き受けない種類のジョブ（段階 3 のワーカーの仕事）は、空きの計算に入れない
  - 司令塔を止めて（再起動・ログアウト）中断した試行は、Mac がオフラインのときと同じく失敗に数えず、戻ったら続きから試す
- すべての質問が `answered`・`dropped` のどちらかになり、`open`・`clarifying`・`revising`・`locked` が 1 つも無くなったら、`checkReadiness` のジョブを作る
- `explain`・`reviseQuestion` の結果は、頼んだ後に状態が変わっていたら書かずに捨てる（説明は問いの人の意図、見直しは質問と依存先の版と回答を、頼んだときと比べる）

### Discussion の写し

人が GitHub の画面で読めるよう、司令塔が状態リポジトリの中身を対象のリポジトリの Discussion に写す。写しは表示と照らし合わせのためだけのもので、正本は状態リポジトリ。Discussion のコメントは指示として読まない（public のリポジトリでは誰でも書けるため。人の意図は `intents/` にだけ置く）。

| 写し | 置く場所 | 中身 | 状態に戻す id |
| --- | --- | --- | --- |
| 依頼 | Discussion の題と本文（カテゴリは「Ideas」） | 依頼の題・本文（引用）・添付の名前、要約、進み具合（epic の段階）、最後の着手前の確認の結果（大きすぎるときは分け方の案） | `epic.json` の `discussion`（番号） |
| 質問 | Discussion へのコメント（質問ごとに 1 つ） | 状態・なぜ・選択肢ごとの変化・推奨と理由・依存（前提にする質問と、この回答で決まる質問）・慎重に決めてほしい理由（警告）・書き直し | `questions.json` の `comment` |
| 説明 | 質問のコメントへの返信 | 人の問いと、その説明（作っている間は「作っています」） | 持たない（目印で探す） |
| 回答 | 質問のコメントへの返信（回答の人の意図ごと） | 選んだ選択肢と補足（人の意図の写し `copy`） | 持たない（目印で探す） |
| ゴール | Discussion へのコメント | 要約・決まったこと・やらないこと・完了の条件・タスク・人がする作業・反映しなかった指示 | `goal.json` の `comment` |

- どこから動かすか: ジョブにせず、常駐のループの周の最後に、状態と写しを照らし合わせる
  - 写しはジョブと試行のファイルを要らない（写しのたびに状態リポジトリに書くと、書き込みの予算を食う）。失敗しても次の周で自然にやり直せ、司令塔を起動し直しても追いつく
  - epic ごとに写しの一式を作り、前に写し終えたとき（司令塔のメモリーに持つハッシュ）から変わっていなければ、GitHub を読まない。1 周で GitHub と照らし合わせる epic は 5 つまで（周を長引かせない）
  - 写す epic は、終わっていない epic と、やめた・マージしてから 24 時間以内の epic（最後の段階を写すため）
- やり直しても重ならない
  - 作る前に、状態に戻した id を見る。無ければ、自分（トークンのアカウント。GraphQL の `viewerDidAuthor`）が書いた目印で探す（作った後、id を戻す前に止まったとき）。ほかの人が書いた目印は読まない
  - Discussion は、epic を作った時刻（から時計のずれの 10 分を引いた時刻）より後に作られたものを新しい順に探す
  - 状態に戻した id の写しがコメントの一覧に無いときは、消されたかを id で確かめる。消されていれば作り直さない（人が消した写しを勝手に戻さない）。消されていなければ一覧が欠けている（GitHub の障害）ので、何も作らずにやり直す。番号の Discussion が見つからないときも作り直さない
  - 写しの id を状態に戻すのは、人の意図の処理・Claude のジョブの結果と同じ排他の中で行う。着手前の確認とゴールの修正の結果は、頼んだ後に写しの id だけが書かれても捨てない（写しの id は判断に使う中身ではない）
- 失敗しても、依頼から開始までの流れを止めない。失敗の区分（[architecture.md](architecture.md)）に沿って epic ごとに間を空け、後の周でやり直す
  - GitHub の障害・上限は間隔を広げて再試行し、この周の残りの写しはやめる。人の対応が要るもの（Discussions が無効・カテゴリ「Ideas」が無い・トークンに Discussions の権限が無い）は 1 時間ごとに試し、司令塔のログに理由を書く
  - Discussions が無効なリポジトリでは、写しを書かない（司令塔のトークンは管理者の権限を持たないので、有効にできない）。有効にするのは「対象に加える」の GitHub 側の準備で行う
- コメントの作成・更新は内容を作る要求なので、状態リポジトリと同じ司令塔の書き込みの予算に数える
- 人と Claude の書いた文はそのまま写す。HTML のコメントの始まり（`<!--`）を崩し、続く本文と目印が隠れないようにする。`@` の直後には見えない文字を入れ、メンションにしない（写しのたびに関係の無い人へ通知が飛ばないように。Claude の文は、リポジトリの中の文章に誘導されて人の名前を書くこともある）。長すぎる本文（6 万文字を超える）は切る

### 質問づくり・説明・確かめを Claude に頼むとき

常時オンの Mac の司令塔が、対象のリポジトリを読むだけの作業場所（clone）で Claude を起動する。

| ジョブ | Claude に渡すもの | 返してもらう形（JSON Schema） |
| --- | --- | --- |
| `makeQuestions` | 依頼（題・本文・添付）、リポジトリの事実 | 質問の一覧（なぜ・選択肢ごとの変化・推奨と理由・依存）と、依頼の要約 |
| `explain` | 質問、それまでの説明、人の問い | 説明の本文と、質問を書き直すならその案 |
| `reviseQuestion` | 質問と、依存先の回答 | そのまま・書き直す（案）・要らない、のどれかと理由 |
| `checkReadiness` | 依頼、質問と回答の一式、何回目か | 進めてよい（ゴールの案）・追加の質問（一覧）・大きすぎる（分け方の案）、のどれか |
| `reviseGoal` | ゴールと、人の指示 | 直したゴール |

- モデルは、このどのジョブも Opus 5.5（`claude-opus-5-5`）。回数が少なく、質が大事なため
- 使えるのは読む道具だけ（ファイルを読む・探す）。書く・コマンドを流す道具は渡さない
- リポジトリの中の文章（README・コメント・ドキュメントなど）に書かれた指示には従わせない（調べる材料として読ませる）。リポジトリの事実（CLAUDE.md の全員向けの事実）は、司令塔が決まりの文に入れて渡す。CLAUDE.md に `## 全員向けの事実` の見出しがあればその節だけを、無ければ全体を渡す（16,000 文字まで。ユーザーの決定）
- 結果が決まりに合わないとき（選択肢の数・依存の循環など）は、`QuestionFlow` で試しに書いてみて、合わない点を伝えて直させる。頼んだ後に状態が変わっていた（人が答え直したなど）ときは、直させずに結果を捨てる
- 結果は `--json-schema` で形を決めて受け取り（結果の JSON の `structured_output`）、司令塔が決まった形かどうかを確かめてから使う。質問の依存は、依存先が実在し、循環していないことを確かめる。合わなければ、同じ会話を再開して直させる（2 回まで）
- 質問の往復は、最初の質問づくりを含めて 3 回まで（`round` は 3 まで。`round` が 4 になる前に、人に「大きすぎる・決めきれない」と出す）。最初の質問づくりは、質問が 1 つも無くても 1 回目と数える。「このまま 1 つで進める」と決めた後だけ、4 回まで
- 1 回の呼び出しの時間の上限は 15 分（質問づくり・確かめ）・10 分（説明・見直し）。超えたら失敗の区分の「時間切れ」として扱う
- 依頼の中身（題・本文・添付）は、ジョブに写さず、実行するときに元の人の意図を読み直して使う（署名を確かめ直す）。添付は、作業場所の clone の外に、ジョブごとのフォルダ（`<フォルダ>/<番号>/<名前>`。名前が重なってもよいように番号で分ける）を作って置き、Claude が読んでよい場所として渡す（質問づくりと着手前の確認）。置く前に、大きさとハッシュを署名した依頼と照らし合わせる（受け付けた後に置き換えられた添付を読ませない）
- 結果を書く前に、epic と質問の一覧とジョブを読み直す。開始した・やめた epic のジョブ、取り消されたジョブ、頼んだ後に状態が変わったジョブ（人が答え直したなど）は、結果を捨て、ジョブは成功として終える
- 結果を書く途中で状態リポジトリの書き込みの予算・GitHub の上限に当たったら、排他の外で待ってから読み直して書き直す（呼んだ Claude の結果を捨てない。待つ間も人の意図の処理は進める）。待つのは合わせて 2 時間まで（`JobTiming.writeWaitLimit`）。2026-11-07 に常時オンの Mac で、予算に当たった結果を書けずに「終えられなかった」で終わり、時間切れの後に Claude を呼び直していた。書き直しは途中まで書いた状態から続ける（追加の質問を書いた後、回答に戻す前に当たったら、続きだけを書く）
- Claude の呼び出しは並んで行うが、結果を読み直してから書き終えるまでと、人の意図の処理は、司令塔の中で 1 つずつ行う（読み直した後、書く前に答え直しが割り込んで、古い結果で先に進めないように）
- 結果から作るジョブ（見直し・着手前の確認）は、元のジョブが結果を書き終えて成功してから動く（`dependsOn`）。途中で止まったとき、書く前の質問の一覧を読んで動かないように。やり直しても、同じ id で作るので 2 つにならない
- 着手前の確認の結果は、`readiness.json`（版を上げる）→ ゴール（版を上げる）か追加の質問 → epic の段階の順に書く。追加の質問を書いた後、回答に戻す前に止まったときは、次の試行が Claude を呼ばずに続きを書く（回答に戻す）
- ゴールの修正の結果は、epic が開始の待ちのままで、ゴールの版が頼んだときのままのときだけ書く（版を上げ、反映しなかった指示を `notApplied` に書く）。決まったこと（`decided`）は回答から来ているので、ゴールの修正では変えさせない（変えていれば、同じ会話で直させる）
- 質問の一覧が無い epic（質問が無くても、質問づくりで空の一覧を作る）は状態が壊れているので、着手前の確認とゴールの修正をせず、人に渡す

## 実装

ワーカーが、ゴールのタスクを 1 つずつ進める。

1. タスクを 1 つ選ぶ
2. Claude にタスクの指示を渡して呼ぶ。Claude は実装と手元の検証まで行い、決まった形で報告して終わる
3. ワーカーが commit・push して子 PR を作る
4. ワーカーが CI とレビューを待つ。待つ間 Claude は動かない。落ちた・指摘があったときは、ログや指摘を付けて同じ会話を再開する
5. マージして状態を書き、次のタスクへ

- タスクの区切りごとに作業ブランチを push しておき、ほかの Mac へ引き継ぐときは最後に push したところから続ける
- ほかの epic が develop に入ったら、タスクの区切りで develop を取り込む
- Claude が報告した仮決めは、「見える（挙動・仕様・見た目に関わる）」か「内部の細部」かの区分つきで記録する。区分は、実装した Claude ではなく、読むだけのレビュー役の Claude が決める。View・文言・アセット・Info.plist・entitlements の差分や、デモモードのスクショの差があれば「見える」とみなす
- 子 PR のレビューは、読むだけのレビュー役の Claude を 1 回呼ぶ。必須の指摘と、仮決めの区分（見える・内部）を返す。CodeRabbit は上限によく当たるので、子 PR では待たず、最終 PR でだけ使う（ユーザーの決定）

### 作業ブランチと子 PR

- 開始すると、司令塔が epic の Mac に作業場所の用意（`prepareWorkspace`）を作る。ワーカーは clone を用意し、`repo.json` の `build.baseBranch`（既定は develop）の最新から作業ブランチ `askhub/<epic の id>` を作って push する。epic の作業場所（worktree）と Simulator の枠も用意する。作業ブランチの名前は `epic.json` の `branch` に書く
- タスクごとに、作業ブランチから子ブランチ `askhub/<epic の id>-<タスクの id>` を作る。子 PR は作業ブランチに、最終 PR は作業ブランチから base に向ける。
  `askhub/<epic の id>/<タスクの id>` にすると、作業ブランチ `askhub/<epic の id>` と git の参照の名前がぶつかって作れない（`refs/heads/askhub/<epic の id>` がファイルとしてあるため）
- 子ブランチは、epic の作業場所（同じ worktree）で取り出し直す。DerivedData を epic の間で使い回せるよう、作業場所のパスを変えない。前の試行が残した手元の変更は捨てる
- リポジトリの事実（CLAUDE.md の全員向けの事実）は、人がレビューしてマージした base の CLAUDE.md から読む。子ブランチの CLAUDE.md は Claude が書き換えられるので使わない
- タスクは、`dependsOn`（ほかのタスクと人がする作業）がすべて終わったものを、ゴールの並びの順に 1 つずつ進める。同じ epic の中でタスクを並べて動かさない

### タスクの流れ

| ジョブ | 動く Mac | すること |
| --- | --- | --- |
| `implementTask` | epic の Mac | Claude に実装させる（下の「Claude にビルドとテストを頼ませる」）。終わったら、ワーカーが commit・push して子 PR を作る。同じ head の開いた PR があれば作らない（作った後、記録する前に落ちても二重に作らない） |
| `reviewTask` | epic の Mac | 子 PR で待つチェック（`repo.json` の `build.childChecks`）を待つ。ランナー不足は間隔を広げて待ち続け、揺らぎ（初めての失敗）は落ちたジョブを 1 回だけ流し直す（ジョブの中で行う）。それでも落ちたら `fixCI`。通ったら、レビュー役の Claude が差分を読み、必須の指摘があれば `fixReview`。無ければ、見た head を固定してマージし、子ブランチを消して `merged`。司令塔がタスクを `done` にして次のタスクへ進む |
| `fixTask` | epic の Mac | CI の失敗（ログの抜粋）かレビューの必須の指摘を付けて、実装の会話を再開して直させ、push する。直しは失敗の扱いどおり 3 回まで。使い切ったら人へ渡す |
| `rerunChecks` | 常時オンの Mac | ランナー不足は間隔を広げて、揺らぎは 1 回だけ、落ちたジョブを流し直す（コードに触れない）。子 PR では `reviewTask` の中で行うので、最終 PR で使う |
| `integrateDevelop` | epic の Mac | タスクの区切りで base が進んでいたら、作業ブランチに取り込む。コンフリクトは Claude に解消させる（3 回まで） |

- Claude が報告した仮決め・見つけた知見・「質問が必要」は、試行の `outputs` に書く。司令塔がそれを `decisions.json`・知見を足す PR・質問に写す
- 子 PR では、macOS のランナーを節約するため、UI テストを含まないチェックだけを待てるようにする（`build.childChecks`）。最終 PR の前に、ワーカーが全部の検証を通す

### 司令塔がタスクを進める

ジョブの中身はワーカーが行い、次にどのジョブを作るかは司令塔が決める（`AskHubCommander` の `TaskFlow`）。司令塔は 1 周ごとに、試行を読んでジョブの状態を決めた後、実装している（`running`）epic ごとに、人の意図の処理と同じ排他の中で、まだ次のジョブを作っていない成功したジョブの結果を読む。

| 成功したジョブ | 司令塔がすること |
| --- | --- |
| `prepareWorkspace` | 試行の `outputs.branch` を `epic.json` の `branch` に書き、最初のタスク（`dependsOn` がすべて済んだ `pending` のもの。ゴールの並びの順）の `implementTask` を作って、`goal.json` のそのタスクを `running` にする |
| `implementTask` | `outputs.report.decisions` を `decisions.json` に足し（`task`・`pullRequest` 付き。`visible` は `null`）、`reviewTask`（`outputs.pullRequest` と、push した head の `outputs.commit`）を作る |
| `reviewTask`（`verdict` が `merged`） | タスクを `done` にし、次のタスクの `implementTask` を作る。すべて済んだら、ログに出して epic は `running` のまま（最終 PR の段取りは後で足す） |
| `reviewTask`（`fixCI`・`fixReview`） | `fixTask`（子 PR と、レビューが見た head。`reason` は `ci`・`review`）を作る。同じタスクの直しが 3 回（`FailurePolicy.maxFixRounds`）を超えたら、作るが動かさずに人の対応待ち（`waitingHuman`）にする（失敗の扱いの「4 回目で人へ」と同じ。人が「やり直す」を送れば、もう 1 回直す） |
| `fixTask` | 実装と同じく仮決めを足し、新しい head（`outputs.commit`）で `reviewTask` を作る |

- タスクのジョブは、epic の Mac（`epic.mac`）に割り当て、ジョブの `task` にタスクの id を書く。元になった人の意図（`origin`）は開始の意図（作業場所の用意のジョブと同じ。ワーカーが署名を確かめる）
- 元のジョブを `dependsOn` に持たせる（`implementTask` は作業場所の用意）。どの結果から作ったかの目印で、子の無い成功したジョブだけを読むので、同じ結果を 2 度読まない
- やり直しても重ならない: ジョブの id は、開始の意図と、`implementTask` はタスクの id、`reviewTask` は元のジョブと head、`fixTask` は元のレビューと直しの回から決める（`ULID.derived`）。書く順は、仮決め → 次のジョブ、ジョブ → タスクの状態で、途中で止まっても次の周で同じものを作ろうとするだけ。同じタスク・子 PR の同じ仮決めは 2 度足さない
- タスクの状態は、司令塔が `pending` → `running`（実装を作ったとき）→ `done`（子 PR をマージしたとき）にする。人が読むゴールの中身は変えないので、ゴールの版は上げない
- 結果が欠けていて進められないとき（作業ブランチ・子 PR・コミット・判定が無い）は、変わるまで何もせず、司令塔のログに 1 度だけ出す

### Claude にビルドとテストを頼ませる

- Claude Code の sandbox の中ではビルドとテストが動かない。そこで Claude は、「ビルドしてほしい（`build`）」「軽いテスト（`testLight`）」「全部のテスト（`testFull`）」を決まった形の報告で返して、いったん終わる。ワーカーが sandbox の外で決まったコマンドを流し、結果の要約を付けて同じ会話を再開する（`--resume`）。往復は、1 つのタスクで上限（20 回）まで
- MCP の道具で頼ませる形は採らない。会社の Claude（Team・Enterprise）では、組織の管理の設定で MCP サーバーが止められていることがある。2026-11-07 に社用 MacBook で確かめ、`--restricted` でも外せなかった。これでは、会社の MacBook のワーカーで使えないため
- Claude に渡す道具は、Read・Edit・Write・Glob・Grep だけにする。Bash は渡さない。道具は `--restricted --tools` で決め、`--settings` の許可の一覧にも同じものを入れる。`--restricted` で、ファイルの読み書きは作業場所（epic の worktree）に限られる
- 報告の形（JSON Schema）は次のとおり
  - `outcome`: `done`・`needsBuild`・`needsQuestion`・`blocked`
  - `buildKind`
  - `summary`
  - `decisions`: 仮決め（`what`・`why`・`alternatives`）。区分はレビュー役が決める
  - `learnings`: 見つけた知見
  - `question`: `needsQuestion` のとき

### 人がする作業

AskHub だけではできない作業（App Store Connect の Web でしかできない設定、外部サービスのプロジェクトの作成など）は、「人がする作業」として扱う。

- 着手前の確認で洗い出してゴールに載せる。途中で見つかったときも同じ扱いにする
- クライアントの「要対応」に、なぜ要るか・手順（入れる値まで具体的に）・開くページ・終わったら渡すもの（設定ファイル・API キーなど）を出す
- その作業を前提にするタスクだけをロックし、ほかのタスクは進める
- 「終わった」を押すか、ファイルを渡したら、ワーカーが確かめられる範囲で確かめてロックを外す
- API キーなどの秘密の値は、クライアントに貼るとそのまま GitHub の Secrets に暗号化して入れる。クライアントにもリポジトリにも残さない

## 最終 PR

### 最終 PR までの段取り

| ジョブ | 動く Mac | すること |
| --- | --- | --- |
| `verifyBeforeFinal` | epic の Mac | すべてのタスクが `done` になったら、最終 PR で流すのと同じ検証（`build.testFull`。UI テストを含む）を通す |
| `classifyDecisions` | 常時オンの Mac | レビュー役の Claude が epic 全体の仮決めを見直し、見える・内部を決めて `decisions.json` に書く |
| `captureScreenshots` | epic の Mac | 見える仮決めの Before（base）と After（作業ブランチ）を、デモモードのデータで撮る |
| `openFinalPullRequest` | 常時オンの Mac | 作業ブランチから base への最終 PR を出す。本文には、判断のカード・実機で確かめてほしいこと・人がした作業を載せる |
| `fixFinalPullRequest` | epic の Mac（オンラインのとき）・常時オンの Mac | 最終 PR の CI の失敗・必須の指摘（CodeRabbit を含む）・コンフリクトを直す。作業場所と DerivedData が温まっている epic の Mac で行い、オフラインのときだけ常時オンの Mac で行う（ユーザーの決定） |
| `reviewFinalPullRequest` | 常時オンの Mac | 最終 PR の待つチェック（`build.finalChecks`）と、信用するレビューの書き手（`build.trustedReviewers`。CodeRabbit など）のレビューを待つ。CodeRabbit が上限で見送ったら待たない（ユーザーの決定）。そのうえで、読むだけのレビュー役の Claude が epic 全体の差分を読み、必須の指摘と、マージの規則の材料（セキュリティのリスク・テストを弱めたか・データの削除や移行）を返す。判定は `ready`（通った）・`fixCI`・`fixReview` |
| `mergeFinalPullRequest` | 常時オンの Mac | マージの規則で自動なら、司令塔がマージする。手動なら、人の承認（`approveMerge`。head に結びつく）を受けてマージする |
| `cleanUp` | epic の Mac | マージの後、作業場所・Simulator の枠・DerivedData を片付ける |

- 流れ: すべてのタスクが `done` → `verifyBeforeFinal` → `classifyDecisions` → `captureScreenshots`（撮影の設定があるときだけ）→ `openFinalPullRequest` → `reviewFinalPullRequest` → 判定が `fixCI`・`fixReview` なら `fixFinalPullRequest` で直して `reviewFinalPullRequest` に戻る（3 回まで）→ `ready` で、マージの規則に当てて自動なら `mergeFinalPullRequest`、手動なら人の判断のカードの答えと承認を待つ → `cleanUp`
- 人が判断のカードで「直してほしい」「別案にする」を選ぶか、最終 PR に指示（`instructFinal`）を出したら、`fixFinalPullRequest` に人の文を付けて直させ、`reviewFinalPullRequest` からやり直す（見える仮決めは、スクショを撮り直して再び出す）
- 承認は、その時点の head に結びつく。直しで head が変わったら、承認は無効になり、承認し直してもらう

### スクショ

- 撮るのは、ビルドの設定に撮影の方法（`build.screenshots`。デモのデータで画面を開いて撮る UI テストなど）があるリポジトリだけ（ユーザーの決定）。無いリポジトリでは撮らず、判断のカードに「スクショ無し（このリポジトリには撮影の設定が無い）」と出す
- 撮影の方法の形と、各リポジトリへの入れ方は、テンプレートの配布（段階 5）で決める。最初の版は「無い」ときの扱いだけを作る

### 出す前に

- 最終 PR を出す前に、最終 PR で流すのと同じ検証（UI テストを含む）をワーカーで通しておく。子 PR では macOS のランナーを節約するため、一部のテストを流さないため

### 失敗の対処

失敗は種類ごとに分けて自動で対処する（区分と既定の扱いは [architecture.md](architecture.md)）。

- ランナー不足は、コードに触れずに間隔を広げて再実行する。上限は設けない。待っていることはクライアントに出すが、「要対応」には入れない
- 揺らぎは、修正の前に 1 回だけ流し直す
- ビルド・テストの失敗、レビューの必須の指摘、コンフリクトは、Claude に 3 回まで直させる
- 自動の修正が、テストを消す・skip にする・Lint を緩めるといった変更をしたら、自動マージの対象から外す
- 対処を使い切ったら、何が起きて何を試したかと、選べる操作をクライアントに出す
- 「マージできます」と出すのは、CI とレビューを本当に通ったときだけ

### 人が決めていない判断の確認

- 「見える」仮決めを 1 つの一覧にまとめて、最終 PR で確認する。ループの途中に仮決めの一覧の Issue は作らない
- 1 件ずつカードにする: 何を決めたか・なぜ（ゴールのどの項目から来たか）・ほかの案・画面の変化（Before / After のスクショ。撮影にはデモモードのデータを使う）
- カードごとに「OK」「別案にする」「直してほしい」を選ぶ。並べて見て「まとめて OK」もできる。「直してほしい」は最終 PR への指示としてループに戻り、直ったらスクショを撮り直して再び出す
- 全部を確認し終えるまで、マージはできない
- 「内部の細部」の仮決めは、畳んで並べるだけにする

### 実機で確かめてほしいこと

- 子 PR ごとの実機確認の Issue は作らない。最終 PR の一覧に「実機で確かめてほしいこと」として入れる
- マージは止めない。TestFlight に上がった後に、クライアントで「確認した」「問題あり」を付ける。「問題あり」は新しい依頼になる（リリース中なら「このリリースを直す」依頼にもできる）
- 確認が溜まらないよう、リリースの「審査に出す」の前に、その版に入った未確認の項目を必ず出し、確かめるか「確かめない」を選ばせる

### マージの規則

| 最終 PR の中身 | マージ |
| --- | --- |
| 人が決めていない判断（見える仮決め）を含む | 人が確認してマージする |
| 見える仮決めが無い（内部の細部の仮決めは含むことがある）、かつ下の手動の条件に当たらない | 自動でマージする（View の改修など） |
| セキュリティのリスクがある | 人が確認してマージする |

- 手動の条件
  - 読むだけのレビュー役の Claude（または CodeRabbit）が、セキュリティのリスクを指摘した
  - 次のものに差分がある: `.github/`、ワークフローから呼ばれる道具、ビルドのスクリプト、`Package.swift` のプラグイン、依存の追加、`.claude/`・`.mcp.json`、entitlements・Info.plist の権限、署名やリリースの設定（`Configs/*.xcconfig`）、トークンや Keychain を扱うコード
  - 自動の修正がテストを弱めた
  - データの削除・移行を含む
- 自動でマージしたときも、何をマージしたかをクライアントに出す
- マージの方式は merge commit
- 人がマージするときの承認は、その時点の head のコミットに結びつける。承認の後に push された変更は、承認し直すまでマージしない
