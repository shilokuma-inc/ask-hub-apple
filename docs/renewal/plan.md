# 進め方

## 作業の場所と作り方

- 今のリポジトリで作り直す。作業は長く使う作業ブランチ `renewal` で行い、PR はすべて `renewal` に向ける
  - develop に入れると、push のたびの Upload で、普段使いのクライアントが作りかけの版に置き換わるため
- 切り替えまで、develop は今の仕組みの不具合の修正だけにする
- 段階 0〜3 は、対話の Claude Code で段階ごとに Issue と PR を切って作る
- クライアントの UI/UX は、人と壁打ちしながら並行して試作する。画面用のモデルはプロトコルの型と分けておき、段階 1〜3 の土台ができたらつなぎ替える

## 段階

| 段階 | 作るもの |
| --- | --- |
| 0. 確かめる | 実装の前提を手元で確かめる（下の「段階 0 で確かめること」） |
| 1. 土台 | プロトコルの定義（JSON Schema・テスト用の例・署名）、状態リポジトリの読み書き、ジョブと試行、Keychain と署名の部品 |
| 2. 依頼から開始まで | 質問（回答・説明を求める・おまかせ・依存のロック）、着手前の確認、ゴール、Mac の選択と開始 |
| 3. 実装から最終 PR まで | ワーカーのタスクの流れ、最終 PR の自動の対処、マージの規則、判断のカード（スクショ）、人がする作業 |
| 切り替えの前提 | 下の「切り替えの前提」 |
| 試運転 | ask-hub-apple と prime-pick-ios で新しい仕組みを試す |
| 切り替え | 全部のリポジトリを新しい仕組みに移し、今の仕組みを片付ける |
| 4. 運用 | 通知の残り、容量の残り、引き継ぎ、片付けの候補 |
| 5. リリースと配布 | 共通リポジトリ、リリース・審査・配信・hotfix、App Store の素材、XcodeGen への移行。1 つの段階にせず、新しい仕組みに流す別々の依頼に分ける |
| 6. Android | Android のクライアントと、Android のリポジトリの開発 |

切り替えの後の段階 4 以降は、新しい仕組み自身で作る。

### 切り替えの後に回すもの

範囲が膨らみすぎないよう、次は切り替えの後に回す。作りは、後から足せる形にしておく。

- 判断のカードの動画（最初はスクショだけ）
- 同じリポジトリでの複数の epic の同時実行（最初は 1 本）
- 「おまかせ」で回す Mac を選ぶ機能
- Android の差し替え部品（境目だけを決めておく）
- Claude の使用率の表示

## 切り替えの前提

試運転の前に、次の最小限をそろえる。これが無いと、切り替えの直後に容量・停止・版のずれで止まり、それを直す手段も無くなる。

- 容量の片付け（ワーカーが作ったもの）と、空き容量の確認
- 生きている印と、GitHub Actions による司令塔の見張り
- Mac の一時停止と再開
- 最小の通知（進行を止めるものだけ）
- ワーカーと司令塔の配り方・更新の手順・版の確認
- Claude Code の版の固定、トークンの期限の表示
- 非常口（Mac のコマンドから署名できる鍵）
- 対象に加える（リポジトリの登録）

## 試運転と切り替え

1. 今の仕組みでは、新しい依頼を出さない。切り替えの時点で終わっていない epic は捨てる
2. 新しいクライアントで今のクライアントを上書きする（今のクライアントは使えなくなってよい）
3. ask-hub-apple と prime-pick-ios を新しい仕組みで回す。この間、ほかのリポジトリの開発は止まる
   - ask-hub-apple は iOS と macOS の両方を持つ
   - prime-pick-ios は、SPM のビルドツールのプラグインと、develop ですでに落ちているテストを持つので、プラグインの扱いと「epic と関係の無い失敗」の扱いを確かめられる
4. 問題が無ければ、残りのリポジトリを対象に加え、今の仕組みを片付ける（下の「残りのリポジトリの移し方」）
5. `renewal` を develop に取り込む

### 残りのリポジトリの移し方

試運転の後、残りのリポジトリを種類ごとに順に移す。

| 順 | 種類 | 理由 |
| --- | --- | --- |
| 1 | iOS だけで、今のテンプレートに近く、課金・拡張が無く、リリースの途中でないもの | 試運転と同じ作りで、まとめて移せる |
| 2 | 課金・ウィジェット・visionOS・macOS・backend など、違う要素を持つもの | 要素ごとに確かめることが違うので、1 本ずつ移す |
| 3 | 配信中のもの、XcodeGen など作りの違いが大きいもの | 審査の合間に移す |

- リリース・審査の途中のリポジトリは、審査が終わってから移す。移す前に、App Store Connect の状態（作りかけの版・審査の状態）を人が確かめる
- 今のオーケストレーターの担当から外れて、今の仕組みの跡だけが残るリポジトリは、今は移さない。跡だけ片付け、要るときに「対象に加える」で足す
- テンプレートは、切り替えでは今の仕組みの跡だけを外す。作り直しは段階 5（共通リポジトリとテンプレートの配布）で行う
- 既存のブランチ保護（クラシックの保護・独自のルールセット）は、「保護の設定」を押したときに新しいルールセットに置き換えて外す。重なると、どれが効いているか分かりにくいため
- 古い形のワークフローは、移すときはそのまま使い、段階 5 の共通リポジトリでそろえる。そのため、リポジトリごとのビルドの設定と CI のチェックの名前を先に持つ（[operations.md](operations.md) の「既存のリポジトリを移すとき」）
- 手動の署名のリポジトリは、移すときに自動の署名（App Store Connect の API キー）にそろえる。provisioning profile の期限切れで Upload が止まらないように

### 切り替えの後始末

- 今の仕組みを止める
  - 常時オンの Mac のオーケストレーターの常駐を止める
  - 各 Mac の見張り役と手動ループを止める
- 捨てる epic を片付ける: epic ブランチ、開いたままの子 PR と最終 PR、制御用の worktree、Simulator、関係する Issue と Discussion
- GitHub 上の残りものを片付ける: 今の仕組みのラベル、状態用の Issue、実機確認の Issue、仮決めの一覧の Issue、依頼の Issue
- 各リポジトリの残りものを外す: ループの仕組みの中継のスクリプトと設定、ゴールの Discussion を閉じるワークフロー、CLAUDE.md のループの節、git で管理している `.claude/settings.json`
- 各 Mac の残りものを片付ける: 制御用の worktree、今のオーケストレーターの設定と退避したデータ、今の仕組みのループが作った Simulator と DerivedData
- 新しい目印は別の名前で、版つきにする（今の目印を読まない）
- 共通の知見の古い項目を直す
- `.coderabbit.yaml` から `renewal` を外し、`renewal` ブランチを消す

## 段階 0 で確かめること

結果は Issue #825 に記録し、この文書の各所に反映した。

| # | 確かめること | 結果 |
| --- | --- | --- |
| 1 | Claude Code の sandbox の中で `xcodebuild`・`simctl` が動くか | 動かない。ビルドとテストはワーカーが sandbox の外で流す |
| 2 | 専用の設定フォルダ（`CLAUDE_CONFIG_DIR`）で人の `~/.claude` が効かないか。リポジトリの hooks・環境変数・`.mcp.json`・CLAUDE.md がどこまで読まれるか | 通常の起動ではすべて効く。`--restricted --strict-mcp-config` と専用の設定フォルダなら、どれも効かず人の指示も見えない |
| 3 | `claude setup-token` で無人実行できるか、使えるモデル、認証の変数の優先順位 | 無人で動く。モデルを指定しないと Sonnet 5.5 になるので、毎回 `--model` で指定する |
| 4 | launchd（ログイン中）から Keychain を読めるか。署名したバイナリを更新しても、Keychain と TCC の許可が残るか | LaunchAgent からは読め、ssh からは読めない。署名したバイナリの更新は、署名の証明書を決めてから確かめる |
| 5 | sandbox の中で `git commit` ができるか（worktree の `.git` は作業場所の外）。partial clone の取り寄せが動くか | commit でき、共有の `.git` にも書ける。Claude には git を許可しない。partial clone はワーカーの作業場所を作るときに確かめる |
| 6 | github.com を許可せず、取得済みの依存だけでビルドできるか | 許可していない宛先には出られない。ビルドはワーカーが sandbox の外で流すので、依存の扱いはワーカーのビルドの道具を作るときに確かめる |
| 7 | 画面の無い launchd の下で、Simulator のスクショと macOS アプリの撮影ができるか | Simulator の作成・起動・スクショ・削除ができる。macOS のアプリの撮影は段階 5 で確かめる |
| 8 | GitHub: 想定の頻度の書き込みでの二次の上限、同時の書き込み、ETag の効き方、複数の organization のトークン | 古い版の書き込みは 409 で弾かれる。ETag つきの読み取りは上限に数えられないとみられる。今の仕組みが動いている間は上限の 3 割ほどが使われている。複数の organization のトークンは、トークンの設計で決める |
| 9 | GitHub: `GITHUB_TOKEN` をブランチ保護の例外に入れられるか、`GITHUB_TOKEN` で作った PR の必須チェック、管理者にも保護を効かせたときの人のマージ | 例外に入れられず、PR も作れない。ルールセットは管理者にも効く。アカウントのトークンの PR なら CI が起動してマージできる。後作業は司令塔の PR で行う |
| 10 | App Store Connect の API: 配信、取り下げとやり直し、App のプライバシーの申告、課金・App Clip・capability | 段階 5 で確かめる（予定） |
| 11 | 利用上限に当たったとき、`claude -p` の出力から解除の時刻を取れるか | 実際に当たったときに確かめる |
| 12 | 今の仕組みで、最終 PR の CI の自動修正が失敗していた原因（常時オンの Mac のログ） | 60 分の時間切れが「結果を読み取れませんでした」に見えていた。失敗の区分に「時間切れ」を持たせる |
