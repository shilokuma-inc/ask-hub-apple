# 進め方

## 作業の場所と作り方

- 切り替え（2026-11-09）までは、長く使う作業ブランチ `renewal` で作り、PR はすべて `renewal` に向けた。切り替えで `renewal` を develop に取り込み、`renewal` は消えた
- 切り替えの後は、PR を develop に向ける。段階 4 以降は、新しい仕組み自身（AskHub の epic）と、対話の Claude Code のセッションの両方で作る
- クライアントの UI/UX は、人と壁打ちしながら並行して試作する。画面用のモデルはプロトコルの型と分けておく

- `addRepository` の処理（`EpicHandlers.swift`）のコメントが「GitHub 側の準備は後で足す」のまま（段階 4 の 4）
- ワーカーと司令塔の配り方: 文書（[operations.md](operations.md) の「署名と公証」。PR #1066）は、どれも常時オンの Mac で Developer ID の署名をして配る形だが、今 Developer ID で署名しているのは司令塔だけで、MacBook Pro のワーカーはアドホック署名（段階 4 の 1。#1064・#1065）
- 各リポジトリの Secrets は、文書（[security.md](security.md) の「public のリポジトリと Secrets」）では Environment の Secrets だが、今は organization の Secrets（#1067）

## 切り替えの前提

試運転の前に、次の最小限をそろえた。

- 容量の片付け（ワーカーが作ったもの）と、空き容量の確認
- 生きている印と、GitHub Actions による司令塔の見張り
- Mac の一時停止と再開
- 最小の通知（進行を止めるものだけ）
- ワーカーと司令塔の配り方・更新の手順・版の確認（版の確認は 2026-11-12 の #1068。配り方は [operations.md](operations.md) の「ワーカーと司令塔の配り方」）
- Claude Code の版の固定、トークンの期限の表示
- 非常口（Mac のコマンドから署名できる鍵）
- 対象に加える（リポジトリの登録）

## 試運転と切り替え

1. 今の仕組みでは、新しい依頼を出さない。切り替えの時点で終わっていない epic は捨てる
2. 新しいクライアントで今のクライアントを上書きする（今のクライアントは使えなくなってよい）
3. ask-hub-apple と prime-pick-ios を新しい仕組みで回す。この間、ほかのリポジトリの開発は止まる
   - ask-hub-apple は iOS と macOS の両方を持つ
   - prime-pick-ios は、SPM のビルドツールのプラグインと、develop ですでに落ちているテストを持つので、プラグインの扱いと「epic と関係の無い失敗」の扱いを確かめられる
   - 試運転のリポジトリに作りかけのリリース（App Store Connect で審査準備中のもの）があっても、移行が終わるまで出さない。そのため、試運転のリポジトリにも新しい保護（ルールセット）を掛けてよい。今の仕組みのリリースの後作業（develop と main に直接 push する）は使わない
   - 出すときは、段階 5 の新しいリリースの流れで出す。作りかけの release ブランチをそのまま使うか、develop から作り直すかは、そのときに決める
   - 結果（2026-11-09）: askhub-sandbox の 3 本、ask-hub-apple の 1 本（renewal 宛て）、prime-pick-ios の 1 本（develop 宛て）が、最終 PR のマージまで通った
4. 問題が無ければ、常時オンの Mac のオーケストレーターを止め、`renewal` を develop に取り込む
   - 取り込む前の develop の先頭にタグ `legacy-final` を付け、今の仕組みのコードを後から取り出せるようにする
   - 残りのリポジトリを移し終えるのを待たない。オーケストレーターを止めれば、develop に今の仕組みの直しを入れる理由が無くなる。残りの移行は、持ち主ごとのトークンや審査の合間を待つので長くかかる
   - 結果（2026-11-09）: オーケストレーターを止め、`legacy-final` を付けて `renewal` を取り込んだ（#972）
5. 残りのリポジトリを対象に加え、今の仕組みを片付ける（下の「残りのリポジトリの移し方」と「切り替えの後始末」）

### 残りのリポジトリの移し方

試運転の後、残りのリポジトリを種類ごとに順に移す。

| 順 | 種類 | 理由 |
| --- | --- | --- |
| 1 | iOS だけで、今のテンプレートに近く、課金・拡張が無く、リリースの途中でないもの | 試運転と同じ作りで、まとめて移せる |
| 2 | 課金・ウィジェット・visionOS・macOS・backend など、違う要素を持つもの | 要素ごとに確かめることが違うので、1 本ずつ移す |
| 3 | 配信中のもの、XcodeGen など作りの違いが大きいもの | 審査の合間に移す |

- リリース・審査の途中のリポジトリは、審査が終わってから移す。移す前に、App Store Connect の状態（作りかけの版・審査の状態）を人が確かめる
- 今のオーケストレーターの担当から外れて、今の仕組みの跡だけが残るリポジトリは、今は移さない。跡だけ片付け、要るときに「対象に加える」で足す
- 担当のリポジトリも、移すのは近いうちに開発するものだけにする。ほかは同じく跡だけ片付け、要るときに足す
- テンプレートは、切り替えでは今の仕組みの跡だけを外す。テンプレートからの新規作成は段階 4 の 5 で作り、共通リポジトリのワークフローを呼ぶ形への作り直しは段階 5 の 5 で行う
- 既存のブランチ保護（クラシックの保護・独自のルールセット）は、「保護の設定」を押したときに新しいルールセットに置き換えて外す。重なると、どれが効いているか分かりにくいため
- 古い形のワークフローは、移すときはそのまま使い、段階 5 の共通リポジトリでそろえる。そのため、リポジトリごとのビルドの設定と CI のチェックの名前を先に持つ（[operations.md](operations.md) の「既存のリポジトリを移すとき」）
- 手動の署名のリポジトリは、移すときに自動の署名（App Store Connect の API キー）にそろえる。provisioning profile の期限切れで Upload が止まらないように
- 段階 4 の 4 ができるまでは、移すときの GitHub 側の準備（Discussions・今の仕組みのワークフローを外す・待つチェックの `paths` の直し・保護）を Claude のセッションが `gh` で手で行う（2026-11-12 までに 9 本をこの形で移した）

### 切り替えの後始末

- 今の仕組みを止める
  - 常時オンの Mac のオーケストレーターの常駐を止める
  - 各 Mac の見張り役と手動ループを止める
- 捨てる epic を片付ける: epic ブランチ、開いたままの子 PR と最終 PR、制御用の worktree、Simulator、関係する Issue と Discussion
- GitHub 上の残りものを片付ける: 今の仕組みのラベル、状態用の Issue、実機確認の Issue、仮決めの一覧の Issue、依頼の Issue
- 各リポジトリの残りものを外す: ループの仕組みの中継のスクリプトと設定、ゴールの Discussion を閉じるワークフロー、CLAUDE.md のループの節、git で管理している `.claude/settings.json`
- 各 Mac の残りものを片付ける: 制御用の worktree、今のオーケストレーターの設定と退避したデータ、今の仕組みのループが作った Simulator と DerivedData
- 新しい目印は別の名前で、版つきにする（今の目印を読まない）
- 共通の知見の古い項目を直す
- `.coderabbit.yaml` から `renewal` を外し、`renewal` ブランチを消す（取り込んだ後、`renewal` 宛ての作業が残っていないのを確かめてから）
- 結果（2026-11-11 まで）: オーケストレーターを止め、今の仕組みのラベル・状態用の Issue を片付け、`.coderabbit.yaml` から `renewal` を外した（`renewal` ブランチは取り込みのときに自動で消えた）。ralph-kit はアーカイブした。
  各リポジトリの残りもの（ralph-kit を呼ぶワークフローなど）と実機確認の Issue は、移すときに片付ける（段階 4 の 4 の「対象に加えるときの GitHub 側の準備」）
